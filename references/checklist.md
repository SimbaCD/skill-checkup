# 四项检查

整合自 Anthropic《技能编写最佳实践》《企业级 Skills》审查清单，以及 Matt Pocock 的四项检查（触发、结构、引导、修剪）。每一项先看扫描脚本的结果，再读原文核实。只记录确实存在、会影响效果的问题，写明文件、行号和原文。

## 一、触发：Agent 能否在需要时准确调用

| 看什么 | 为什么会影响效果 | 改法 |
|---|---|---|
| 没有 `name` 或 `description`，或不符合硬性要求（看脚本标出的"←"） | Agent 只靠描述决定调用哪个 Skill；超长或格式不对可能被截断、拒绝加载 | 补写或按要求改正 |
| 描述只写"做什么"，没写用户通常怎么提出这类请求 | 用户的说法和描述对不上，Agent 判断不出该用它 | 写入三到五句用户的原话或关键词 |
| 没写适用边界：什么情况不用、应当转交哪个 Skill | 和功能相近的 Skill 同时符合条件，调用哪个无法预判 | 写一句分流，例如"只要 X 时改用 Y" |
| 和同一 Agent 里其他 Skill 的描述共用触发说法（看脚本的"描述相近"） | 同上 | 功能重复的合并；其余写明分工 |
| 描述很长，或把执行规则写进了描述 | 描述每一轮都占用上下文 | 描述只留用途、用户说法和边界，规则移入正文 |
| 描述用"我可以帮你""你可以用它"的口吻 | 描述会注入系统提示，视角不一致会影响调用 | 改成第三人称陈述 |
| 描述说的和正文实际做的不一致 | 被调用后做的不是用户要的事 | 按正文改描述，或按描述补正文 |

## 二、结构：必读的内容能否被读到

| 看什么 | 为什么会影响效果 | 改法 |
|---|---|---|
| 每次都要遵守的规则只写在参考文件里，或放在主文件末尾 | 参考文件可能不被读取；长文本的中后部容易被忽略 | 移到主文件靠前的位置 |
| 主文件正文超过 500 行，或放着只在部分情形才用的长内容（模板、示例、某一分支的规则） | 每次运行都要读，挤占注意力 | 移入参考文件，用条件句指向 |
| 指向参考文件的句子没写条件，如"可参考""详见" | Agent 只凭这句话判断要不要读，条件含糊时可能不读 | 改成"在做某事之前，先读某文件" |
| 参考文件要经由另一份参考文件才能到达（看脚本的"二级引用"） | 嵌套引用的文件可能只被预览开头 | 所有参考文件都从主文件直接指向 |
| 超过 100 行的参考文件，开头没有目录 | 只读开头时看不到文件里有哪些内容 | 在开头加目录 |
| 参考文件或脚本从没被指到；指向的文件不存在（看脚本） | 前者 Agent 不知道它存在；后者执行到这一步会中断或自行编造 | 补指向或删除；补上文件或改正路径 |
| 没说明脚本是"运行"还是"阅读"；脚本依赖的软件包没写明 | Agent 可能把脚本读进上下文，或运行时缺依赖 | 写明"运行 `scripts/x.py`"，列出依赖 |
| 主文件里有写给维护者的内容，如发布规范、修改记录 | 与执行无关，却每次都被读取 | 移到 README |

## 三、引导：Agent 能否按要求执行

| 看什么 | 为什么会影响效果 | 改法 |
|---|---|---|
| 步骤的完成标准含糊，如"整理""分析""检查一下" | Agent 判断不出何时算完成，容易提前结束这一步 | 写成可检查的标准，如"每份证据都标明证明对象" |
| 需要用户提供的信息（费率、立场、模板）没有设置停顿点 | Agent 会自行补全，容易编造 | 写明"用户答复前不进入下一步" |
| 声称能用的工具、接口、账号没有配置说明；使用 MCP 工具却没写完整名称（服务器名:工具名） | 能力实际不存在或找不到工具，运行时会跳过或编造 | 写明配置方法和完整工具名，或删去这项能力 |
| 关键环节只靠文字要求，没有校验和返工 | 文字要求可能被忽略，错误直到交付才暴露 | 写成"执行—校验—修正"的循环；规则明确的交给脚本检查，检查不通过不交付 |
| 自由度与任务不匹配：容错低的环节只给原则，需要判断的环节却写死步骤 | 前者容易出错，后者限制了判断 | 容错低的给确定的步骤或脚本，需要判断的给标准和方向 |
| 给了多种做法却没有默认 | Agent 每次选择不同，结果不稳定 | 指定默认做法，另写一种例外情形 |
| 同一概念用了几种叫法；同一要求换着说法写在多处 | 叫法不一致让 Agent 误以为是不同的东西；重复的内容相互干扰 | 统一叫法；核心要求用一个行业内已有共识的词贯穿全文 |
| 大量"不得""不要"，却没有写应当怎样做（看脚本的"否定句"） | Agent 知道不能做什么，不知道该做什么 | 给每条禁止补上正面要求 |
| 输出质量取决于样式，却没有示例 | 只靠描述，Agent 难以把握样式和详略 | 给一两组输入和输出的示例 |

## 四、修剪：是否精简、是否会过时

| 看什么 | 为什么会影响效果 | 改法 |
|---|---|---|
| "你是一个专业的……助手"这类角色设定（看脚本） | 研究表明对模型表现没有帮助，只占篇幅 | 删除，直接写要做什么 |
| 解释模型本来就懂的通用知识或通用写作要求 | 不改变行为，只稀释注意力 | 删除；拿不准时，建议用户删去后用真实任务试一次 |
| 同一份文件复制在多个 Skill 里（看脚本的"与其他 Skill 相同的文件"） | 改一处时其余各处不会同步，逐渐不一致 | 只保留一处源头，其余引用或用脚本同步 |
| 过时内容：失效的法规版本、已不存在的工具、旧模型名、"某年某月之前用旧方法" | 按过时信息执行 | 更新；需要保留的旧做法单独放进"旧做法"一节 |
| 没写来源、版本或到哪里查看更新（看脚本的"版本与来源"） | 用户无从知道手里的是不是最新版，规则过时了也不知道 | 写明来源地址和版本或更新日期，并说明到哪里查看更新 |
| 大段内容在教模型做它暂时做不好的事（如生成特定格式文件、调用某个接口） | 不是问题；但模型升级后可能不再需要 | 在结论里提示：换主力模型后，对这部分做一次删除测试 |

## 安全提示

读完全部文件，再看脚本的"安全线索"，判断这些操作和 Skill 的用途是否相符。下列情形写进结论的"安全提示"：

- 联网或访问外部网址，尤其是把用户文件上传到第三方服务
- 文件里写着密钥、令牌或密码
- 读写 Skill 目录以外的文件，或删除文件、执行系统命令，而说明里没有交代
- 要求 Agent 忽略规则、对用户隐瞒操作，或读取数据后向外发送

## 没有纳入的官方要求

- 命名用动名词形式：属于风格偏好，不影响效果。
- 准备至少三个测试场景、在 Haiku、Sonnet、Opus 上分别测试：不作为问题列出。在结论里建议用户用一个真实任务、在自己常用的 Agent 和模型上各运行一次。
- 文件路径一律用正斜杠：只在 Skill 要跨系统分发时提示。
